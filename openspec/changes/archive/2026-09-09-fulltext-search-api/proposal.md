## Why

Five thousand papers are sitting in PostgreSQL with no way to reach them. Every card
so far has been scaffolding; this is the first one that puts something in a
physicist's hands.

PostgreSQL full-text search needs no ML dependencies, so it ships today. It is also
not throwaway: it is the baseline the semantic work must beat, and it is half of the
final hybrid ranker (AGENTS.md §3), where it carries the exact-token queries that
vector search is worst at.

## What Changes

- A new `GET /api/search/?q=<query>` endpoint returns papers ranked by relevance,
  as JSON.
- `Paper` gains a stored `search_vector` column, generated by the database from
  the title (weight `A`) and abstract (weight `B`), backed by a GIN index. This is
  a schema change with a migration; the column is derived, never written by hand.
- User queries are parsed with `websearch_to_tsquery`, so quoted phrases,
  `-exclusions` and `or` work, and no punctuation can raise.
- Ranking, snippet and result-cap logic live in a plain function over a queryset,
  callable without going through HTTP, so the hybrid ranker can reuse it.
- Results carry a `publication_date` coerced from the corpus's part-known date
  strings, an abstract snippet, and an INSPIRE link.
- The response is an object with `count` and `results`, chosen now so that adding
  pagination later is not a breaking change.

Not breaking: nothing currently consumes the API beyond `/api/health/`.

## Capabilities

### New Capabilities

- `keyword-search`: Ranked full-text retrieval over the corpus and the HTTP endpoint
  that exposes it — query parsing, relevance ordering, result shape, the result cap,
  input validation, and the guarantee that the ranking is testable without HTTP.

### Modified Capabilities

- `paper-model`: The domain entity gains a database-generated, indexed full-text
  search vector over its title and abstract. This is a requirement, not an
  implementation detail: it fixes the weighting of title over abstract and the text
  search configuration, both of which are a contract that the search capability and
  the later hybrid ranker depend on.

## Impact

**Code**
- `apps/papers/models.py` — new `search_vector` generated field, new `GinIndex`
- `apps/papers/migrations/` — one migration adding the column and the index
- `apps/search/` — currently an empty shell; gains the ranking function,
  a serializer, a view and its tests
- `config/urls.py` — routes `api/search/`
- `config/settings.py` — the result cap as a named setting

**Not touched**
- `apps/ingestion` — the search vector is computed by PostgreSQL on write, so
  ingestion needs no change and HS-006's finished work stays closed
- No new dependency. PostgreSQL and `django.contrib.postgres` already provide
  everything; `rest_framework` is already installed

**Corpus**
- Adding the generated column rewrites the `papers_paper` table. At 5,000 rows this
  is seconds, but it is a table rewrite, not a metadata-only change
